## Proposed AWS architecture

The team has selected a separated application, worker, and database shape for planning. This is a proposed target, not a deployed system. AWS Learner Lab currently permits `us-east-1` and `us-west-2`; `us-east-1` is the planning region for this design, not a statement about an existing deployment.

- **Public web/API:** one EC2 instance in a public subnet runs Nginx and the React frontend, and proxies API requests to FastAPI on the same host. A DuckDNS hostname is the chosen hostname approach. The actual hostname, TLS certificate, and OAuth callback configuration are not set up.
- **Private processing:** one private worker EC2 instance runs two bounded processes: PDF extraction/cleanup and MiniLM CPU embedding. Pin the application and model images in ECR. The worker polls its own SQS queue and reads required input from S3. It does not serve public traffic.
- **Queues:** use separate SQS queues for extraction and embedding, each with its own dead-letter queue. The proposed processing policy allows up to three attempts total, including the initial attempt, for transient failures; an unusable PDF is terminal and should not be retried pointlessly. SQS `maxReceiveCount` counts receives, not guaranteed worker executions, so it must be tuned with visibility-timeout behavior rather than described as an exact execution count. Exact visibility timeout, redrive settings, task identity/retention, and operational values remain TBD. Duplicate delivery must not duplicate or overwrite a user's accepted operation.
- **Files:** private S3 stores uploaded PDF objects; the database reference identifies the PDF for the latest explicitly saved revision. Keep the previous current PDF reference until a reviewed save commits, then remove the old object in separate cleanup. Embedding failure does not undo the saved PDF reference. Downloads use short-lived URLs issued only after authenticated ownership checks. Provide explicit file and account deletion. The cleanup interval for failed or abandoned uploads remains to be selected.
- **Database:** private RDS PostgreSQL, Single-AZ, with pgvector planned. The subnet group spans a second Availability Zone for placement coverage; this does not create a standby or high availability. The 2026-09-26 [Learner Lab capability evidence](LEARNER_LAB_CAPABILITIES.md) records PostgreSQL 16 minor versions and burstable classes offered in the console, plus a candidate `db.t3.micro`/20 GiB gp2 configuration. No database was created; exact pgvector compatibility remains unverified.
- **Network and observability:** one NAT gateway is provisional for private worker outbound access; use an S3 gateway endpoint. Workers poll their respective SQS queues and fetch input from S3; S3 traffic uses the gateway endpoint. The transactional-outbox publisher's placement and network path are TBD; do not infer a separate AWS service or claim that the API request directly publishes to SQS. CloudWatch logs and metrics are selected, while exact alarms and thresholds remain open.
- **Permissions:** Learner Lab supplies a pre-created `LabRole`. The team cannot claim custom per-component least-privilege IAM roles under that constraint. Specific role permissions and security-group rules still need to be recorded and checked. Enhanced Monitoring is unsupported in this lab; standard available monitoring can be used.

## User and processing flow

1. The authenticated browser submits a PDF to the API. The API validates ownership and input, stores the upload in private S3, then commits extraction task state and an outbox instruction in the database. It returns `202 Accepted` with a task identifier after the S3 object exists and that database transaction commits; queue publication may lag. A publisher retries durable unsent outbox rows and marks a row sent only after SQS acknowledges publication. Duplicate publication is possible, so task handling is idempotent. Publisher placement and transport are TBD.
2. The browser polls the authenticated API for task status. It can continue browsing while extraction runs. Polling returns `202` while the accepted task remains pending; task lookup is scoped to the authenticated owner.
3. The extraction process consumes the extraction queue, reads the PDF from S3, and writes a reviewable draft and extraction status to PostgreSQL. The agreed processing policy is up to three attempts total for transient failures, including the initial attempt; an unusable PDF is terminal. SQS receive count is not the exact number of worker executions, so `maxReceiveCount` and visibility timeout require tuning. Extraction failure is visible in task status and follows the bounded retry/DLQ policy.
4. The user reviews and edits the extraction draft in the browser. Human review is an explicit boundary: the extraction process writes only a reviewable draft and extraction status. It never creates the initial approved profile. No embedding job is published until the user explicitly saves the reviewed content.
5. On explicit save, the API uses one database transaction to record the approved content as a new revision, point the user at the already-uploaded PDF reference for that revision, set embedding status to `PENDING`, and create the durable embedding task plus outbox instruction. The API may return accepted after this transaction commits; queue publication may lag while a publisher retries durable unsent rows, marking them sent only after SQS acknowledges. Duplicate publication is possible and must be idempotent. Publisher placement is TBD; no new AWS service is implied. The embedding process creates CPU MiniLM vectors and writes vectors plus embedding status for the current revision only. It never writes or replaces approved profile content. A worker must guard the revision and task identity/status in the atomic database commit after computation; checking only before computation is insufficient. A late worker for an old revision or a superseded task must discard its result without changing current revision status. Matching can use only the current revision when its embedding status is `READY`; stale vectors must not be mixed with the current revision. If embedding fails, preserve the approved content and its PDF reference, mark matching preparation failed, and expose retry; do not present that revision as ready for matching.
6. The uploaded PDF object already exists in S3 before explicit save. The save transaction promotes its database reference to current alongside the reviewed revision; this database change and the S3 upload are not atomic together. Keep the previous PDF reference until that transaction commits, then remove the old object as separate cleanup. If review is abandoned, the previous current PDF remains referenced. Explicit user/account deletion removes associated stored files. The retention period for failed and abandoned uploads remains open.

The transactional outbox and revision-guard behavior above are proposed and not implemented or verified. Retry creates a new task attempt for the currently saved revision and reuses its existing PDF reference; it does not reupload the PDF or reset the old failed task, so a late old worker cannot overwrite the new attempt. Reconciliation must distinguish queued work still awaiting publication or processing from stuck or failed work, and use task state/lease-aware checks; exact cadence, lease, and timeout are TBD. The logical task flow, publisher placement, queue tuning, cleanup interval, and concurrency sizing need implementation and resilience tests. Useful verification cases include: a crash after database commit but before publication; duplicate publication; worker crash; attempt A completing after revision B is saved; an obsolete attempt completing after a retry; and embedding failure retaining the reviewed approved content and PDF reference. A ten-minute recording is an assumption about recording duration, not total provisioning or billing time. Clarification from the professor about required environment uptime is pending.

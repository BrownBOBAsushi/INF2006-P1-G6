## Proposed AWS architecture

The team has selected a separated application, worker, and database shape for planning. This is a proposed target, not a deployed system. AWS Learner Lab currently permits `us-east-1` and `us-west-2`; `us-east-1` is the planning region for this design, not a statement about an existing deployment.

- **Public web/API:** one EC2 instance in a public subnet runs Nginx and the React frontend, and proxies API requests to FastAPI on the same host. DuckDNS is the proposed hostname approach. The actual hostname, TLS certificate, and Google Authorized JavaScript origin (`APP_ORIGIN`) are not configured. Google Identity Services uses a JavaScript callback, not a server OAuth redirect URI.
- **Private processing:** one private worker EC2 instance runs two bounded processes: PDF extraction/cleanup and MiniLM CPU embedding. Pin the application and model images in ECR. The worker polls its own SQS queue and reads required input from S3. It does not serve public traffic.
- **Queues:** separate SQS queues for extraction and embedding, each with its own dead-letter queue, are selected. The database attempt count increments on a successful task claim and is authoritative; automatic redelivery is the same task attempt, while a user-requested retry creates a new task linked to the current revision. SQS `maxReceiveCount` is a safety net set above the DB attempt limit; it counts receives, not worker executions. After every terminal DB transition, including attempts exhausted, the worker deletes the message. Reconciliation marks a task `FAILED` when its lease expires after the last attempt. Visibility timeout must exceed the 60-second processing deadline plus S3/DB time, or be extended by the worker. Duplicate delivery must not double-count attempts or overwrite a newer revision. Exact values remain TBD.
- **Files:** private S3 stores candidate uploads and the latest explicitly saved PDF. The database reference identifies the saved PDF for the latest explicitly saved revision. Keep the previous current PDF reference until a reviewed save commits, then remove the old object in separate cleanup. Embedding failure does not undo the saved PDF reference. Downloads use short-lived URLs after authenticated ownership checks. Explicit file and account deletion must remove owned objects; failed/abandoned candidate cleanup has a selected retention interval and lifecycle backstop. These are proposed behaviors and are not implemented.
- **Database:** private RDS PostgreSQL, Single-AZ, with pgvector planned. The subnet group spans a second Availability Zone for placement coverage; this does not create a standby or high availability. The 2026-09-26 [Learner Lab capability evidence](LEARNER_LAB_CAPABILITIES.md) records PostgreSQL 16 minor versions and burstable classes offered in the console, plus a candidate `db.t3.micro`/20 GiB gp2 configuration. No database was created; exact pgvector compatibility remains unverified.
- **Network and observability:** one NAT gateway is provisional for private worker outbound access; use an S3 gateway endpoint. Workers poll their respective SQS queues and fetch input from S3; S3 traffic uses the gateway endpoint. The transactional-outbox publisher is a small loop process on the public API host, using its internet-gateway path to SQS; no separate publisher service is proposed. CloudWatch logs and metrics are selected, while exact alarms and thresholds remain open.
- **Permissions:** Learner Lab supplies a pre-created `LabRole`. The team cannot claim custom per-component least-privilege IAM roles under that constraint. Specific role permissions and security-group rules still need to be recorded and checked. Enhanced Monitoring is unsupported in this lab; standard available monitoring can be used.

### S5.1-A02 architecture decision record — synchronous foundation

**Decision status:** The current proposal selects an AWS hybrid service model: IaaS EC2 for the public web/API host and managed PostgreSQL RDS for the private database. The deployment model is one public AL2023 EC2 host for Nginx and the synchronous API, with a private Single-AZ RDS instance. This records the design choice for review; it does not claim professor or team-owner sign-off, resource permission, or authorization to provision. Formal team confirmation remains unrecorded.

**Alternatives considered:**

| Alternative | Trade-off for this foundation | Decision |
|---|---|---|
| One VM for web, API, and PostgreSQL | Fewer AWS components and a simpler initial network; database lifecycle, storage, backup, and failure recovery would share the public application host. | Not selected because the current design keeps PostgreSQL private and managed separately. |
| Public API/web EC2 plus private managed RDS (selected) | Keeps the existing synchronous API shape, gives the team control over the host runtime, and separates database placement and lifecycle. It requires VPC/security-group, TLS, host recovery, and RDS permission checks; it remains a single API host and a Single-AZ database. | Selected proposal, subject to Learner Lab permission and the gates in the foundation runbook. |
| Managed application/container hosting or serverless functions with managed database | Could reduce host administration or scale selected request paths, but would change deployment/runtime assumptions and needs service, networking, IAM, and cost permissions that have not been established in this Learner Lab. Short-lived functions also do not remove the need to validate the current model-loading/API behavior. | Not selected for this first synchronous proof; reconsider only after checking lab support and the measured workload. |

The service-model comparison is IaaS compute (EC2) plus managed database service (RDS), versus a more managed application/container or function service with managed database. The deployment comparison includes the all-in-one VM and the separated application-host/private-database layout. The current Learner Lab evidence lists EC2 and RDS choices and records an allowed EC2 dry-run, but does not prove create permission for all resources or establish managed application-service availability. This ADR does not close those operational gates or assert that the coursework marker has accepted the choice. The separate later async proposal is not part of this synchronous foundation decision.

## User and processing flow

1. The authenticated browser submits a PDF to the API. The API validates ownership and input, stores the upload in private S3, then commits extraction task state and an outbox instruction in the database. It returns `202 Accepted` with a task identifier after the S3 object exists and that database transaction commits; queue publication may lag. A small publisher loop on the public API host retries unsent outbox rows and marks a row sent only after SQS acknowledges. Duplicate publication is possible, so task handling is idempotent.
2. The browser polls the authenticated API for task status. It can continue browsing while extraction runs. Polling returns `202` while the accepted task remains pending; task lookup is scoped to the authenticated owner.
3. The extraction process consumes the extraction queue, reads the PDF from S3, and writes a reviewable draft and extraction status to PostgreSQL. Up to three successful processing claims are allowed for transient failures, including the initial claim; duplicate delivery while a valid lease is active does not increment attempts. A fresh claim after a failed/expired lease increments once. Unusable PDF is terminal. SQS receive count is not exact worker executions; set `maxReceiveCount` above the database attempt limit as a safety net. Terminal DB transitions delete the message, and final expired lease/DLQ work reconciles to `FAILED`.
4. The user reviews and edits the extraction draft in the browser. Human review is an explicit boundary: the extraction process writes only a reviewable draft and extraction status. It never creates the initial approved profile. No embedding job is published until the user explicitly saves the reviewed content.
5. On explicit save, the API re-runs privacy cleanup synchronously before any save-side effect. If cleaned content differs, it returns `422 REVIEW_REQUIRED` with the cleaned draft; it creates no revision, successful SaveOperation, embedding task/outbox row, or PDF promotion until the user reconfirms. After confirmation, one DB transaction records approved content as a new revision, promotes the owner-checked upload selected by `upload_id`, sets embedding status to `PENDING`, and creates the embedding task/outbox instruction. A non-null upload ID must be a current unpromoted candidate owned by the session and tied to the expected profile revision. `upload_id: null` means a manual save: it promotes no candidate and preserves the separately identified latest explicitly saved PDF; its recorded source revision may differ from the manually edited content revision, and downloads are labelled as the original uploaded PDF. A first manual save has no PDF. `SaveOperation` becomes `SUCCEEDED` once this transaction commits; embedding progress/result is separate task/revision state. The embedding process creates CPU MiniLM vectors and writes vectors/status only if the task and revision are current at atomic commit. Late workers discard results. Matching can use only current-revision `READY` vectors. If embedding fails, preserve approved content and the latest saved PDF; expose retry as a new task for that revision using saved content (embedding does not read the PDF).
6. The candidate PDF exists in S3 before explicit save. The save transaction promotes its reference to current alongside the reviewed revision; this database change and S3 upload are not atomic together. Keep the previous PDF reference until that transaction commits, then remove the old object as separate cleanup. If review is abandoned, the previous current PDF remains referenced; candidate lifecycle cleanup is the backstop. Authenticated users can download only their latest explicitly saved PDF through a short-lived URL. File deletion and account deletion must remove owned stored files, with in-flight task handling defined before implementation. Account deletion is a planned task, not a current API capability.

The transactional outbox and revision-guard behavior above are proposed and not implemented or verified. SQS redelivery keeps the same task identity; each fresh DB processing claim increments its attempt count once, while duplicate delivery under a live claim does not. A user retry creates a new task with a new identity. Extraction retry uses the saved candidate PDF; embedding retry uses the saved approved content and does not read a PDF. Terminal transitions, including attempts exhausted, delete the SQS message; a DLQ safety-net redrive/final expired lease reconciles to `FAILED`. Reconciliation distinguishes unsent outbox rows and active leased work from stale tasks. Exact cadence, lease, timeout, and `maxReceiveCount` remain TBD. Tests cover commit-before-publish crash, duplicate publication/delivery, retry accounting, poison/DLQ reconciliation, worker crash, stale revision completion, and embedding failure. A ten-minute recording is not total provisioning or billing time. The course brief explicitly permits decommissioning after evidence capture; retained or disposable lifecycle is a cost decision.
